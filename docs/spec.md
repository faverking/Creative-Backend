# MonoNest AI 编码 Spec

## 1. 定位

这份文档是 MonoNest 的 AI 编码约束，优先级高于其他 docs。

- `docs/spec.md` 只放稳定边界、职责分层、数据一致性和场景硬规则。
- `docs/overview.md` 只放工程事实和入口索引。
- `docs/workflows/*` 只放命令、构建、测试、提交与部署流程。
- `docs/API接口与参数说明.md` 只讲接口协议。
- `docs/业务与架构设计说明.md` 只讲业务规则和架构设计。
- `docs/工程目录与运行指南.md` 只讲运行、环境、部署和排障细节。

当前仓库是基于 `NestJS + MongoDB + JWT/OAuth` 的内容平台后端，服务 `MonoApp` 的公开内容、管理端治理、媒体、搜索推荐和用户互动。

## 2. 新会话读取顺序

1. `docs/spec.md`
2. `docs/overview.md`
3. `docs/workflows/README.md`
4. 按任务命中读取：
   - 接口：`docs/API接口与参数说明.md`
   - 业务规则：`docs/业务与架构设计说明.md`
   - 运行部署：`docs/工程目录与运行指南.md`

## 3. 执行总则

- 不使用破坏性 git 命令；不回退用户已有改动，除非用户明确要求。
- 先贴合现有模块化单体结构，不平行新建第二套入口、服务或协议。
- 不为了分层而分层；抽象必须来自真实重复、职责失衡或稳定边界。
- 不保留兼容代码、旧字段、旧 DTO、双轨 mapper、fallback 协议、临时别名或冗余分支。
- 先做小而完整的收口，不做大而松散的重构。
- 行为迁移时同步清理残留代码、测试与文档。
- 后端不保存前端展示占位策略，只保存真实业务值或语义一致的空值。

## 4. 模块与分层边界

默认分层：`Controller -> Service/Application -> Repository -> Schema`。

- `controller`：路由、鉴权、DTO 校验、参数拆解。
- `service/application`：业务编排、事务边界、副作用协调、结果映射。
- `repository`：数据访问与查询表达。
- `schema`：集合结构、索引和持久化字段。
- `common/`：守卫、装饰器、拦截器、公共常量与工具。
- `infra/`：数据库、Redis、日志、存储、审计、指标等基础设施。
- `workspace/`：跨内容摘要、关系清理、访问记录等内部能力，不单独暴露 HTTP 控制器。

只有当服务职责明显失衡或重复逻辑跨模块稳定出现时，才拆 presenter、query service、command service 或共享 util。

## 5. 数据一致性

先判断链路类型：

- 强一致：内容主记录、收藏关系、评论根记录、回复记录、`favorCount`、`replyCount`、权限、可见性、后台治理、管理审计。
- 最终一致：历史、通知、用户侧审计、非关键侧写。

规则：

- 强一致主链路不能接受“主记录成功、关系或计数失败但仍返回成功”。
- 最终一致不等于静默失败，必须保留明确日志。
- 生产环境强一致链路依赖 MongoDB 事务；生产默认不允许事务不可用时降级为非事务执行。
- 删除、设私密、永久删除都必须评估收藏、历史、通知、评论可见性、精选配置、个人中心列表和计数清理。
- 读取链路可以自愈旧脏关系；能在命令链路一次清掉的，优先在命令链路清掉。
- API 返回要显式稳定，对外标识字段转字符串，不依赖 `ObjectId` 隐式序列化。

## 6. API 与前后端契约

- 优先复用现有路由语义和资源命名，不随意引入别名。
- 返回结构围绕当前前端真实消费模型设计，不为未来假设堆字段。
- 不在接口层加入临时兼容字段或新旧字段双轨。
- 对外协议统一 `camelCase`；存储层字段统一 `snake_case`。
- 公开接口只返回可公开内容。
- 前端能用展示层兜底的问题，不污染后端数据模型。
- 如果前端请求方式和后端设计意图冲突，先确认真实请求链路，再决定是否改协议。

## 7. 业务场景硬规则

### 评论

- 继续使用“根评论分页 + 回复预览 + 完整回复单拉”的线程模型。
- 不提前改递归树，不提前上双层分页。
- 评论列表 `total` 表示根评论总数；回复列表 `total` 表示该根评论下回复总数。
- 详情主接口 `replyCount` 表示总讨论量。
- 新增根评论：总讨论量 `+1`，根评论总数 `+1`。
- 新增回复：总讨论量 `+1`，根评论总数不变。

### 收藏、历史、通知

- `POST /favorites/toggle` 是收藏关系统一入口，关系变化后同步回写目标内容 `favorCount`。
- 历史记录是最近访问模型，不是完整行为流水。
- 通知读模型优先满足可定位、可跳转、可标记已读，不堆额外 viewer state。

### 后台治理

- 管理员设私密、取消精选、永久删除必须处理关联清理。
- 后台治理和管理审计属于强一致链路。
- 后台列表、个人中心列表和公开读取口径不能互相漂移。

### 媒体

- 上传、预览、下载、ZIP 解包/打包要区分 HTTP 行为，不混用 `preview` 与 `download`。
- 调整媒体能力时检查大小限制、并发参数、临时文件、持久化目录和 PM2 内存上限。
- 运行时代码依赖必须放在 `dependencies`，不能只放 `devDependencies`。

## 8. 已移除旧字段

不要恢复或兼容以下历史字段：

- 图包：`width`、`height`
- 书籍：`hots`
- 游戏：`scheduleLabel`

## 9. 校验矩阵

改动后运行与范围匹配的最小有效校验；无法运行时说明原因。

| 改动范围 | 默认校验 |
| --- | --- |
| 业务逻辑、DTO、service/application、repository、schema | `pnpm test` + `pnpm lint` + `pnpm build` |
| 单个模块窄改 | 相关 `.spec.ts` + `pnpm lint` + `pnpm build` |
| 部署、依赖、PM2、生产运行 | `pnpm build` + `pnpm deps:prod:check` |
| 数据库索引 | `pnpm db:indexes:sync` 仅在明确需要同步索引时执行 |
| 文档 | `git diff --check -- docs` 或等价 Markdown 检查 |

生产依赖检查必须在 `pnpm build` 之后运行。

## 10. 何时更新本 spec

出现以下变化时，同步更新 `docs/spec.md`：

- 调整模块边界、分层规则或共享横切能力。
- 修改数据一致性、删除清理、评论、收藏、通知、历史或后台治理模式。
- 调整 API 协议、公开可见口径或前后端契约。
- 调整媒体处理、生产依赖、部署发布或回滚链路。
- 移除或恢复历史字段。
