# MonoNest Implementation Spec

本文件用于约束后续在 `MonoNest` 仓库中的代码实现、接口设计、重构与审查行为。

目标只有三个：

- 保持实现贴合当前后端结构
- 保持业务语义与数据一致性稳定
- 避免为了兼容、抽象或“未来可能需求”引入冗余代码

## 1. 通用约束

### 1.1 结构优先级

- 必须优先贴合当前仓库的模块化单体结构：`Controller -> Service/Application -> Repository -> Schema`
- 新功能优先落到现有模块边界内，不平行新建第二套入口、第二套服务或第二套协议
- 只有在现有模块职责已经明显失衡、且抽离后边界清晰时，才允许拆 presenter、query service、command service 或共享 util

### 1.2 实现风格

- 不保留兼容代码，不做新旧双轨并存
- 不保留冗余字段、冗余分支、冗余 DTO、冗余 mapper
- 不为了“看起来更解耦”而额外引入事件总线、适配层、空 façade、空抽象
- 抽象必须来自真实重复和稳定边界，而不是来自主观偏好
- 优先做小而完整的收口，不做大而松散的重构

### 1.3 数据与返回约束

- API 返回必须显式、稳定、可预期，不依赖 `ObjectId` 的隐式序列化行为
- 对外返回的标识字段应统一转成字符串
- 展示占位逻辑留在前端，后端只保存真实业务值或语义一致的空值
- 不把“默认图片地址”“前端占位文案”一类展示策略写入业务数据

### 1.4 一致性优先

- 只要某字段直接参与业务展示、搜索排序、推荐打分、后台统计或权限判断，就按强一致处理
- 只要某链路属于用户侧侧写、行为留痕、通知投递、历史记录等次级写入，就可以按最终一致处理
- 最终一致不等于静默失败，必须保留明确日志
- 强一致主链路不能接受“主记录成功、计数或关系未同步但仍返回成功”

### 1.5 代码审查标准

- 先看数据一致性，再看接口语义，再看结构优雅度
- 重点排查：脏关系、脏计数、可见性穿透、权限不统一、删除后残留、私密后残留、分页 total 与实际 items 不一致
- 如果一个实现只是“能跑”，但会造成语义漂移或未来维护混乱，也应视为缺陷

### 1.6 交付要求

- 只要修改了业务逻辑，就优先补最小必要测试
- 完成后默认执行：
  - `pnpm test`
  - `pnpm lint`
  - `pnpm build`
- 改动接口、架构边界或文档事实时，需要同步更新文档，避免文档漂移

## 2. 场景约束

### 2.1 新增或调整 API

- 优先复用现有路由语义和资源命名，不随意引入别名
- 返回结构必须围绕当前前端真实消费模型设计，不为潜在未来场景提前堆字段
- 不在接口层引入“临时兼容字段”或“同时支持新旧字段”
- 如果要做破坏性收口，应直接替换到最终协议，不保留旧协议残影

### 2.2 重构服务或模块

- 只有当重复逻辑已跨模块出现、或者单个服务体量和职责已经明显失控时，才做拆分
- 拆分后必须让边界更清晰，而不是让调用链更长
- presenter 只负责响应拼装
- query service 只负责读
- command service 只负责写、事务、清理和副作用编排
- 不允许把简单问题重构成难以追踪的多跳调用

### 2.3 计数、关系与侧写

- `favor_count`、`reply_count`、类似业务主计数属于强一致
- 收藏关系、评论根记录、回复记录与业务计数必须同步收口
- 历史、通知、用户侧审计默认按最终一致处理，但失败必须可观测
- 清理链路允许容错，但不能让主链路留下脏数据

### 2.4 删除、私密、后台治理

- 用户删除、管理员设私密、管理员永久删除，都必须评估并处理关联数据清理
- 至少要检查：收藏、历史、通知、评论可见性、相关计数、后台列表、个人中心列表
- 读取链路如果发现旧脏关系，可以自愈；但能在写入/命令链路一次清掉的，优先在命令链路清掉

### 2.5 评论系统

- 继续坚持“根评论分页 + 回复预览 + 完整回复单拉”的线程模型
- 不提前改成递归树，不提前上双层分页
- 评论列表的 `total` 只表示根评论总数
- 回复列表的 `total` 只表示该根评论下的总回复数
- 详情主接口中的 `replyCount` 表示总讨论量
- 新增根评论时，总讨论量 `+1`，根评论总数 `+1`
- 新增回复时，总讨论量 `+1`，根评论总数不变
- 评论和通知中的作者头像允许为空，不强行要求用户先上传头像

### 2.6 通知、历史、审计

- 通知、历史、用户侧审计属于侧写链路，默认不阻塞主业务
- 但安全、后台治理、后台精选等管理动作的审计必须保持强一致
- 通知返回结构应优先满足前端可定位、可跳转、可标记已读，不堆叠额外 viewer state
- 历史记录保持轻量，默认用于“最近访问”，而不是行为流水

### 2.7 前后端契约

- 如果前端可以通过展示层兜底解决的问题，不要污染后端数据模型
- 如果后端字段语义已经稳定，前端应配合消费，不在后端继续叠兼容
- 如果发现“前端请求方式”和“后端设计意图”冲突，优先先确认真实请求链路，而不是在后端补猜测性兼容

### 2.8 文档治理

- 文档应少而准，不堆重复说明
- 能合并的文档就合并，避免一份事实散落多处
- 审查文档可以阶段性存在，但最终有价值的结论应回收到正式文档
- 接口文档只讲协议，业务设计文档讲规则与边界，运行文档讲目录、环境与排障

## 3. 明确不做的事

- 不为了未来假设需求提前铺复杂能力
- 不为了兼容保留旧字段、旧分支、旧路径
- 不为了抽象而抽象
- 不把前端占位策略写进后端业务数据
- 不让计数、关系、权限和可见性各走各的口径

## 4. 默认工作方式

后续实现默认遵循以下顺序：

1. 先读现有模块与文档，确认真实边界
2. 先识别主链路与侧写链路
3. 先保证数据一致性，再做结构优化
4. 只做必要抽象，不留兼容残影
5. 补测试，跑 `test / lint / build`
6. 同步文档，确保实现与文档一致

如果后续需求与本文件冲突，以用户当前明确要求为准；否则默认按本规范执行。
